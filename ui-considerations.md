## Key interactions to design for

- **Scan → capture loop.** One-tap into the scanner from Home; auto-decode on detection (no manual shutter), a brief "wild beast!" reveal, then a capture confirm. Support **gallery/photo import** as a fallback (some barcodes are hard to hit live). Offer "scan another" and "done" so bulk scanning is fast.
- **Duplicate handling.** Same barcode = same beast. Decide: does rescanning grant XP/coins, level up, or just a toast? Show a "already owned" state clearly rather than a dead-end.
- **Battle invite via QR.** P1's screen shows a large, high-contrast QR (with a fallback **short code/link** they can type or share by text). P2 scans it to join. Consider: QR expiry/TTL, a "waiting for opponent" spinner, and a manual code-entry fallback for camera failures.
- **Sharing animals.** Two distinct paths — (1) share to a friend who *adds* it to their collection, (2) share as a battle. Use a beast-encoding payload (QR or deep link) so the receiver's device deterministically reconstructs the same creature.
- **Deterministic generation.** Because the same barcode must produce the same beast on every device (so trades/battles are fair), generation must be a pure function of the barcode — no per-device randomness. This is the single most important constraint for your data model.

## Offline / local-first (your "store to device, sync later" requirement)

Treat the **local store as the source of truth** and the network as optional enrichment:

- **Write locally first, queue for sync.** Every scan/battle result is written to local storage (SQLite/Room/Hive) immediately with a locally-generated stable ID and a `sync_status` (`pending` / `synced` / `conflicted`). A background worker (WorkManager / a connectivity listener) drains a durable **outbox queue** in order when connectivity returns.
- **Render from local, tag pending items.** Show "syncing…" or a subtle pending badge on unsynced beasts; never block the user on a network call.
- **Conflict resolution.** For a creature collector, **last-write-wins** on simple fields (level, XP) is usually fine; use **field-level merge** if two devices can edit the same beast offline. Model deletes as tombstones so a device that was offline for a long time doesn't resurrect a deleted beast.
- **Idempotency.** Use the local ID as an idempotency key on upload so a retried sync can't create a duplicate server-side record.
- **The one thing that must NOT be offline:** the **live battle** between two devices. Local QR invite works only if both players are physically together — so the battle itself needs a real-time channel (WebRTC / a small relay) *or* a turn-based async model where each player's moves are queued and exchanged. Decide this early, because it's the hardest part and it's what your offline storage does *not* cover.

## Edge cases worth planning UI for

- **Camera permission denied** → fallback to photo-from-gallery + manual code entry.
- **No barcode / unreadable** → clear "didn't detect a code" state, retry, and manual-entry option.
- **QR invite scanned but opponent offline / already in a battle** → graceful error, not a crash.
- **Storage full / very large collection** → pagination in the bestiary, not one giant list.
- **First launch with no network** → the app must still be fully playable (scan + local battle vs. AI or a second local profile); don't gate core play behind connectivity.

## Suggested MVP cut

Ship in this order: **Scan → Beast Detail → Bestiary → local Battle (vs. AI or local) → QR invite Battle → Share → Settings/sync.** Get the deterministic generator and the local-first store solid first; the QR-invite real-time battle is the riskiest feature and benefits from being last.
